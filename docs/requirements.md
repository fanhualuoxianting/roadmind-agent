# RoadMind Agent 需求说明

> 文档状态：阶段 0 审查通过（开发基线）
> 更新日期：2026-08-03
> 项目性质：智能座舱 Agent 工程演示，不接入真实车辆

## 1. 项目背景

RoadMind Agent 面向“人—车—家”协同出行场景，用一个可解释、可确认、可验证的任务型 Agent 展示 Java 后端、AI 应用和 Agent 工程能力。项目重点不是聊天界面或汽车知识问答，而是把自然语言目标转换成可审计的结构化计划，并在受控环境中完成多工具执行。

本项目为智能座舱 Agent 工程演示项目，与小米汽车及其他汽车厂商无官方关联。车辆控制、车辆位置和车辆状态均通过数字孪生模拟服务实现。

## 2. 项目目标

### 2.1 产品目标

1. 支持用户用自然语言描述复杂出行目标，并通过多轮对话补齐或修正关键信息。
2. 将目标拆解为有依赖关系、可校验的结构化任务计划。
3. 统一接入车辆、天气、地图、充电、定时任务和智能家居工具。
4. 对写操作执行权限、参数、风险、确认、幂等和频率控制。
5. 使用数字孪生模拟车辆状态、指令执行和沿真实道路的行程。
6. 通过 SSE 实时展示 Agent 状态、工具调用和车辆遥测。
7. 对关键执行结果进行二次验证，并保留完整审计证据。
8. 建立可重复运行的 Agent 评测集，只公开真实执行结果。

### 2.2 求职展示目标

项目需要能够清晰证明以下能力：

- Java 21 与 Spring Boot 工程实践；
- Agent 任务规划、多轮上下文和结构化输出；
- 工具注册、选择、授权、执行、验证和失败恢复；
- MySQL、Redis、SSE、外部 API 与 MCP 集成；
- 安全边界、风险确认、幂等、审计和可观测性；
- Vue 3 智能座舱界面与实时地图交互；
- 自动化测试、评测、Docker Compose 和开源维护。

## 3. 目标用户

| 用户 | 主要诉求 | 系统提供的价值 |
| --- | --- | --- |
| 演示用户 | 用一句话规划复杂出行任务 | 多轮补充、计划预览、风险确认、实时执行反馈 |
| 求职面试官 | 快速判断项目是否真正具备 Agent 工程深度 | 可追踪计划、工具调用、策略拦截、验证和评测证据 |
| 开源阅读者 | 本地运行并理解架构 | 明确边界、可复现启动方式、模拟数据和完整文档 |
| 项目维护者 | 在 10～14 天内完成首个可演示版本 | 渐进式模块划分、阶段验收和受控范围 |

## 4. 核心演示场景

用户输入：

```text
明天早上 8 点从南京去苏州接朋友。车现在电量不多，帮我规划一下。天气冷的话提前开空调，出门后把家里的灯关掉。
```

核心流程：

1. 读取会话状态和长期偏好，解析相对时间时固定用户时区。
2. 从车辆数字孪生读取电量、续航、位置、胎压和车内温度。
3. 提取起点、终点、时间和附加任务；缺失或冲突时要求补充。
4. 查询出发时段天气并规划真实道路路线。
5. 计算能耗，必要时生成提前充电或中途充电方案。
6. Planner 生成结构化计划，后端校验 Schema、依赖和工具参数。
7. Policy Gate 从服务端工具注册表读取真实风险级别。
8. 查询类步骤自动执行；需要确认的写操作进入等待确认状态。
9. 用户查看目标、参数、影响和过期时间后逐项或批量确认。
10. Executor 使用幂等键创建定时任务，Verifier 回查任务是否真实存在。
11. 到达计划时间后执行模拟预热、导航和关灯任务。
12. 启动车辆数字孪生行程，地图沿高德规划道路展示模拟位置。
13. SSE 持续更新速度、电量、位置、剩余距离、ETA 和 Agent 状态。
14. 低电量、天气或路线事件触发规则检查和受控重新规划。
15. 完成后输出成功、部分成功或失败结果，并写入审计日志。

## 5. 功能需求

### 5.1 会话与上下文

- 创建、查询和关闭会话。
- 保存当前目标、实体槽位、待确认操作、已执行步骤和工具结果摘要。
- 支持“从学校”这类长期偏好映射。
- 支持用户修正已有实体；新值覆盖旧值并记录变更来源。
- 区分短期会话状态和长期偏好，分别设置保留策略。
- 对传入模型的上下文做裁剪、摘要、脱敏和不可信内容标记。
- 信息缺失、歧义或冲突时，不得擅自执行写操作。

### 5.2 Planner

- 将用户目标转换为符合 DTO/JSON Schema 的计划。
- 计划包含目标、实体、步骤、依赖、参数和计划版本。
- Planner 只提出工具请求，不直接调用工具。
- 非法 JSON 先做一次受约束修复；仍失败则使用规则降级或返回可解释错误。
- 后端校验未知工具、循环依赖、缺失依赖、非法参数和超大计划。
- 模型输出的风险级别仅作无效输入丢弃，最终风险由工具注册表决定。

### 5.3 Policy Gate

- 工具风险分为 `READ_ONLY`、`LOW_RISK_WRITE`、`HIGH_RISK_WRITE`。
- 校验身份、车辆或家庭资源归属、工具权限和参数白名单。
- 对高风险写操作要求一次性、短时有效、绑定计划版本和参数摘要的确认。
- 拦截重复提交、过期确认、参数被篡改和未授权调用。
- 对可疑 Prompt Injection、异常频率和敏感参数做基础拦截与审计。

### 5.4 Executor 与 Verifier

- 仅执行通过 Schema 校验和 Policy Gate 的步骤。
- 统一处理参数转换、超时、有限重试、熔断、幂等和错误分类。
- 记录 `executionId`、`traceId`、开始/结束时间、输入摘要和输出摘要。
- 只对只读调用或明确支持幂等的写操作重试；高风险操作不得换幂等键重试。
- 关键写操作必须回查目标系统验证，不以 HTTP 200 或 `success=true` 作为唯一成功依据。
- 支持成功、部分成功、验证失败和失败后停止依赖步骤。

### 5.5 工具体系

第一版工具：

```text
vehicle.get_status
vehicle.schedule_climate
vehicle.lock
vehicle.get_scheduled_tasks
weather.get_forecast
route.plan
charging.find_stations
charging.calculate_strategy
home.control_device
schedule.create_task
schedule.cancel_task
```

每个工具必须声明名称、版本、输入类型、输出类型、风险级别、超时、重试策略和验证器。工具实现不得散落在 Controller 中。

智能家居首版使用 `MockHomeGateway` 与版本化模拟设备状态实现，不新增家居微服务。页面、API 和审计必须标注 `SIMULATION`，Verifier 通过只读回查确认灯具状态。

`schedule.create_task` 首版只允许创建普通提醒等明确白名单任务，不接受任意 `toolName + args`。延后执行车辆或家居动作时，仍以原始 `vehicle.*` / `home.*` 步骤参与风险分级和确认，调度器只保存已授权的执行意图，不能通过低风险包装器降低风险。

### 5.6 车辆数字孪生

- 查询和修改模拟车辆状态。
- 模拟定时空调、锁车、任务执行、电量变化和位置变化。
- 使用独立 `VehicleGateway` 接口隔离调用方与模拟实现。
- 模拟指令具有明确的状态机、延迟、失败注入和幂等行为。
- 页面和接口响应明确标注 `SIMULATION` 或 `DIGITAL_TWIN`。
- 不实现或暗示任何真实小米汽车或其他厂商认证与控制能力。

### 5.7 地图与行程

- 使用高德地图 JS API 2.0 展示中国境内地图。
- 路线服务返回有序坐标、道路距离、预计时间和充电站候选。
- 展示起终点、已行驶路线、未行驶路线、车辆和充电站。
- 车辆图标按 heading 转向，并在遥测点之间平滑插值。
- 支持开始、暂停、继续、取消、重置和 1x/5x/20x 倍速。
- 支持低电量事件与动态重新规划。
- 地图密钥缺失或加载失败时进入降级视图，不影响对话、计划和日志。

### 5.8 智能座舱前端体验

主界面不是传统后台，也不是只有气泡的聊天机器人。桌面优先布局为：

```text
左侧：Agent 对话、补充信息和用户输入
中间：真实道路地图、路线与模拟车辆
右侧：车辆数字孪生状态、天气与行程摘要
底部：Agent 执行时间线和工具调用状态
浮层：高风险操作确认
```

需要规划并逐步实现的视图：

1. 智能座舱主界面；
2. Agent 任务规划详情；
3. 实时车辆行程地图；
4. 高风险操作确认弹窗/抽屉；
5. 工具调用与审计日志；
6. 车辆数字孪生状态面板；
7. Agent 评测结果；
8. 系统能力与模型配置状态。

核心状态必须有独立可见设计：初始空状态、Agent 分析、等待补充、等待确认、工具执行、部分成功、工具失败、SSE 断开、遥测延迟、地图不可用、模型不可用和行程完成。页面始终区分“已计划”“等待确认”“已执行”“已验证”，避免用户把计划当成结果。

### 5.9 实时事件

- SSE 推送 Agent 生命周期、工具调用、确认状态、行程状态和遥测。
- 每个事件包含稳定的事件 ID、递增序号、事件类型、时间和 `traceId`。
- 支持心跳、断线重连、`Last-Event-ID`、去重、完成和错误事件。
- 行程遥测建议每秒产生一次；前端不依赖网络频率直接移动图标。

### 5.10 定时任务

- 持久化定时任务、目标时间、时区、参数摘要、状态和幂等键。
- 服务重启后能够恢复未执行任务。
- 支持创建、取消、领取、执行、验证和过期处理。
- 到期任务由带租约的单实例/多实例安全 Worker 领取，避免重复执行。
- 车辆原生预热定时命令由 `vehicle-simulator` 保存和执行；RoadMind 定时任务负责跨域编排、家居动作、启动行程与提醒，两者不得重复创建同一副作用。

### 5.11 审计与评测

- 查询计划、工具调用、用户确认、策略拦截、状态变更和执行结果。
- 审计记录追加写，业务更新不能覆盖历史证据。
- 第一批不少于 30 条评测用例，覆盖正常、异常、安全、多轮和实时场景。
- 指标从实际评测运行产生，不在 README 或简历中预填数字。

## 6. 非功能需求

### 6.1 安全

- 密钥、密码和 API Key 不得硬编码或提交到 Git。
- 使用环境变量和未提交的本地配置；后续提供 `.env.example`。
- 日志默认脱敏，不记录原始密钥、完整令牌和高敏感参数。
- 所有写操作具备权限、参数、风险、确认和幂等检查。
- 浏览器采用会话 Cookie 时，所有修改请求必须校验 CSRF；CORS 只允许显式来源。

### 6.2 稳定性

- 外部模型、地图和天气调用有明确超时、熔断和降级路径。
- Redis 或地图故障不得使基础会话与审计完全不可用。
- 模型不可用时允许规则化展示已有状态和提示用户稍后重试，不伪造模型结果。
- 错误分类可区分用户输入、策略拒绝、外部依赖、系统错误和验证失败。

### 6.3 可维护性

- 使用稳定、明确版本，不使用 `latest`、SNAPSHOT 或动态范围。
- 数据库结构使用 Flyway 版本化迁移，不依赖运行时自动建表。
- 核心领域不直接依赖地图、模型或车辆厂商 SDK。
- 模块有真实职责，禁止为展示架构创建空壳模块。
- Windows PowerShell 命令和路径必须可用。

### 6.4 可测试性

- 模型、地图、天气、车辆和家居均通过接口适配，可替换为测试实现。
- 数据库与 Redis 集成测试使用 Testcontainers。
- 时间、随机数和 ID 生成器可注入，避免定时与状态机测试不稳定。
- SSE、幂等、确认过期、断线恢复和低电量重规划必须有自动化测试。

### 6.5 性能与容量边界

首版按单用户演示设计，不宣称生产级吞吐。建议限制：

- 单次用户输入不超过 8 KiB；
- 单计划步骤不超过 20 个；
- 单会话活跃 SSE 连接不超过 3 个；
- 单次模型规划设定 Token 上限和超时；
- 遥测原始流在 Redis 短期保留，MySQL 只存状态变化和降采样数据。

实际阈值需在阶段 7 结合测试调整。

## 7. 明确的非目标

- 不接入或伪造真实车辆控制 API。
- 不宣称获得小米汽车、小米集团或其他厂商授权。
- 不制作普通聊天机器人或汽车知识问答系统。
- 不在第一版实现 Three.js 城市场景、赛车玩法或高精地图。
- 不在第一版实现完整车机操作系统、自动驾驶或真实导航播报。
- 不做 Kubernetes、服务网格、Kafka 等与演示目标无关的基础设施。
- 不将所有模块拆成微服务。
- 不为追求技术栈数量引入无业务职责的中间件。
- 不伪造测试、性能、评测或外部 API 结果。

## 8. 第一阶段范围（阶段 1）

阶段 1 仅建立可运行骨架和车辆模拟闭环：

- 创建 Java 21 / Spring Boot 工程和 Vue 3 工程；
- 使用 Docker Compose 启动 MySQL 与 Redis；
- 使用 Flyway 创建阶段 1 实际需要的最小表并通过空库迁移测试；
- `vehicle-simulator` 可独立启动；
- 通过 HTTP 查询车辆模拟状态并修改至少一个状态；
- 写操作有参数校验；
- 有单元测试和接口测试；
- 不依赖真实大模型也能启动基础服务；
- README 提供 Windows PowerShell 命令。

阶段 1 不实现 Planner、完整工具调用、MCP、地图行进、长期记忆或完整评测。

## 9. 最终完成标准

项目同时满足以下条件才视为首个完整版本：

1. 核心演示场景可从输入、补充、计划、确认一直执行到行程完成。
2. Agent 计划通过结构校验，工具风险由后端配置决定。
3. 未确认的高风险操作被稳定拦截，确认后使用同一参数摘要和幂等键执行。
4. 逐项/批量确认均保存独立 item 决策，未批准项不会随其他项执行；崩溃恢复不生成新幂等键。
5. 车辆沿真实规划道路进行明确标注的数字孪生模拟，路线来源可区分 LIVE、CACHE 与 STUB。
6. SSE 支持断线重连、去重、心跳和完成事件。
7. Verifier 能识别至少一种“调用成功但目标状态不匹配”的情况。
8. 模型、地图或 Redis 故障均有可演示的错误或降级状态。
9. MySQL、Redis、后端、模拟器和前端可按 README 在 Windows 上启动。
10. 自动化测试和不少于 30 条 Agent 评测用例可重复运行。
11. README、架构图、演示脚本、截图/GIF 和免责声明完整。
12. 仓库不包含密钥、密码、本地绝对路径或 IDE 私有配置。
13. 所有公开指标来自实际运行并附有执行方法和时间。

## 10. 需求优先级

| 优先级 | 范围 |
| --- | --- |
| P0 | 上下文修正、结构化计划、风险确认、工具执行、Verifier、车辆模拟、实时地图、SSE、审计 |
| P1 | 长期偏好、定时任务恢复、低电量重规划、故障注入、评测页面、MCP 服务 |
| P2 | 多模型配置、更多家庭设备、更多地图提供商、复杂评测分析 |
